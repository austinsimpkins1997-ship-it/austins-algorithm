# Security policy

This public Apache-2.0 project includes a local Workbench, classical simulators and optimizers, persistent job/project stores, explicit file imports/exports, and optional provider integrations. Its default CPU, Planning, practical-check and Security Lab workflows do not submit provider jobs. The optional IBM preflight authenticates and reads a selected backend; the explicitly configured physical comparison can submit a bounded paid/quota-consuming job. These are separate boundaries, not a universal offline guarantee.

The Workbench Assistant uses local rules. The experimental backend interface does not grant a plug-in provider access or permission. An in-process Python predicate or plug-in is executable code; use only trusted implementations. Treat imported JSON, traces, archives, source text and reports as data, and verify supported inputs before use. A checksum or local signature compares bytes; it does not prove source truth, consent or a trusted Windows publisher.

Saved projects, local reports and incident exports are not automatically confidential or encrypted. Store sensitive work only in an approved protected location and review its contents before sharing. Job integrity records do not provide multi-user authentication or tenant isolation. Keep API keys, personal information and confidential data out of repository history, examples, issues and exported evidence.

## Provider and deployment boundaries

Select the saved account, backend, instance and budget explicitly. A client timeout does not prove cancellation. Reconcile the original job ID or ambiguous submission through the provider before retrying; usage can accrue after failure/cancellation. Dry-run mock output is not physical correctness evidence. Unknown pricing, privileges and usage stay unknown. No live authentication enforcement, general cracking service, production sandbox, remote administration, organization-wide identity or compliance certification is supplied by the synthetic Security Lab.

The program remains alpha and Windows publisher-unsigned. Representative human acceptance, deployment-specific security/privacy/accessibility review, operational ownership, recovery and a configured private vulnerability intake remain required for a production setting. Consult IBM_HARDWARE.md and PRACTICAL_EVIDENCE.md before external execution.
