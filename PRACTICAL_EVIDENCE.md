# Practical evidence and acceptance (0.3.2 alpha)

Reviewed November 17, 2026. Editor: Codex (AI assistant), at Austin's request. This update improves measurement and reporting; it does not implement a practical quantum advantage or certify production acceptance.

## Run the matched check

In the Windows Workbench, open Overview and select **Run CPU comparison & export**. Choose a parent folder; a new timestamped evidence folder is created. This runs a fixed public teaching problem, independently checks complete answer sets, and exports protocol, raw trials, readable summary, the source decision ledger and integrity manifest. It does not modify the active project or contact a provider.

```powershell
python -m austins_algorithm practical-check --output NEW-EVIDENCE-DIRECTORY --repeats 32 --shots 64 --seed 701
```

The same Python API is `practical_evidence.benchmark()` followed by `export_benchmark(new_directory, result)`. The range is 1–128 trials and 1–256 shots per trial. Defaults are declared before the comparison, alternate execution order, and retain failures. A one-shot run cannot recover both answers; it is an informative failed completeness check, not discarded data. CLI correctness failures return a nonzero exit status. Outputs never overwrite an existing directory.

Each method must return both valid answers (`011` and `101`). The reference constructs them directly from the public constraints. The candidate is the existing CPU ideal simulator, including its exhaustive predicate preprocessing, sampling and independent output checks. Repeated seeds are not fresh problems, physical trials, or a demonstration of quantum advantage. The short local measurements retained in `.build/acceptance-20261117` favored direct construction; microsecond timings do not establish a general ratio or a hardware forecast.

## Physical comparison accounting

The existing `compare` workflow now reports a `practical_evidence` summary and a 95% Wilson hit-rate interval based on completed shots. The interval assumes IID Bernoulli samples; correlated noise, drift, selection and repeated-circuit effects can violate it. All-success finite samples do not prove success probability one. Output correctness, sampling estimates and ideal mathematical support remain separate fields.

Provider usage collection preserves completed, pending, estimated and unknown status. Conflicting modern/legacy usage fields hold the value as unknown. Reported zero completed usage is distinct from missing usage. On a failed or timed-out submitted job, fetch usage once and retain its original ID; no automatic resubmission or cancellation occurs. A failure/cancellation can still incur usage. Exceptions are reduced to their class so account details are not copied into evidence.

Queue/running durations, client wall time, provider usage and monetary cost are different quantities. They overlap; adding them can double count time. An execution cap limits provider quantum usage; a client wait timeout does not cancel the provider job. Actual plan pricing is not inferred from QPU seconds, a local circuit duration or a simulator. Monetary cost stays unknown when no billing evidence exists.

Cloud dry-run jobs require an authorized eligible plan and account and return randomized mock data. They are neither local simulation nor physical measurements. This update does not enable or submit dry-run jobs. The existing local/real-backend guards and explicit `dry_run=False` physical submission path remain. A named backend still requires its actual supported target to compile and verify; a hardware announcement creates no device entitlement.

## Program acceptance

The source suites, built-wheel identity, actual installed hidden native workflows and bounded planning references are technical evidence for the local alpha. They do not substitute for a human operator, independent reviewer or named deployment approver. The prepared acceptance protocol and signed phase-one record are under `.build/acceptance-20261117`; no operator measurements were invented. Windows publisher signing, hosted identity/tenant controls, deployment security/privacy/accessibility and production acceptance remain unverified. The unrelated legacy homophone browser journey remains separate and unresolved.

To resume the physical experiment, configure a legitimate provider account locally, identify a useful nontrivial workload, named backend/instance and allowed shots/time/paid-use budget, then use the existing preflight and explicitly authorized submission. Keep keys out of chat and exports. To accept the program in an organization, name the deployment, accountable owner and representative human checks first. This documentation is not approval or a schedule.
